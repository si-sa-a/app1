# AI活用PBIレビューアプリ導入 Before / After

## 施策概要

AIを活用してPBI（プロダクトバックログアイテム）のたたき台を自動生成し、
リファインメントの質を向上させる。

- AIの役割: PBI草案・受入条件・確認事項・DORチェックリストの**たたき台生成**
- チームの役割: リファインメントで議論・ブラッシュアップ・**DOR Ready判定**
- DORチェックはチーム全員で実施（コミュニケーション活発化のため）

### ゴール

1. PBIの書き方を知らなくてもテンプレート（ユーザーストーリー形式＋受け入れ条件）に沿って一定品質のPBIを作成できる
2. PBIの不足情報や考慮漏れをAIが自動指摘し、リファインメントの材料にすることができる
3. リファインメントでチーム全員がDORチェックを行い、Ready判定ができる

## Before / After 比較

### 1. PBI作成プロセス

| 観点 | Before（現状） | After（導入後） |
|------|---------------|----------------|
| 作成方法 | PO（開発メンバー）が手作業でPBIを記入している | 自然言語で要求を入力すると、AIがテンプレートに沿ったPBIを自動生成する |
| 品質のばらつき | PBIの記載内容が書き手の経験やスキルに依存し、品質にばらつきがある | AIがテンプレートに沿って整形するため、誰が作成しても一定の品質が担保される |
| 受け入れ基準 | 受け入れ条件の記載が曖昧だったり、書かれていない | AIが正常系・異常系・を含めた受け入れ条件を自動提案し、抜け漏れを防止する |
| DOR（Ready判断）導入 | PBIのReady判断基準がなく、プランニング時に初めて内容を確認している | DORを基準にリファインメントでPBIの準備状況を事前に確認し、Ready状態のものだけをプランニングの対象とする |
| スプリント中の仕様確認 | PBIの記載が不十分なため、実装中に仕様の確認・問い合わせが頻発 | PBIの記載が明確になることで、スプリント中の仕様確認が大幅に減少する |
| 手戻り | 仕様の認識齟齬により、レビューやテスト段階での手戻りが発生 | 受け入れ条件が事前に明確化されることで、認識齟齬による手戻りが減少する |

## 期待される効果（まとめ）

| 指標 | 期待される改善 |
|------|--------------|
| PBI作成時間 | 50〜80%短縮 |
| スプリント中の仕様確認 | 減少 |
| 手戻りによる追加工数 | 減少 |

---

## 導入リスクと対策

| リスク | 対策 |
|--------|------|
| AIの出力を鵜呑みにする | AIはたたき台。チームが判断・修正する運用ルールを設定 |
| 導入コスト・学習コスト | まず2〜3件のPBIで試行し、効果を確認してから展開 |
| 合わなかった場合 | ツール依存ではなくプロセス改善。いつでも元に戻せる |
